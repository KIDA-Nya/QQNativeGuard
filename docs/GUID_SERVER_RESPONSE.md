# GUID 换新后的服务端反应（2026-11-25 10:23）

## 实验结果

**GUID 从 `<orig-guid-16B>` 换成 `<fake-guid-16B>`（完全不同的 16 字节），重新登录后：**

| 观察项 | 结果 |
|---|---|
| 登录验证提示 | **无**（无“设备存在风险”、无“新设备验证”） |
| KICK_TO_LOGIN | 0 |
| RISK_OBSERVE | 0 |
| GUARD_EXIT | 0 |
| 界面 | 直接进主界面 |

## 与历史对照

| 场景 | 变化的标识 | 服务端反应 |
|---|---|---|
| V6 换机型 | 机型 LE2123 → PGEM10 | **要求“新设备验证”** |
| **本次换 GUID** | GUID 全新 | **无验证，直接放行** |

## 两种解释

### 解释 A：GUID 不是设备识别的主锚点

服务端靠其它标识（QIMEI / AndroidID / 机型 / serial）认设备，
GUID 只参与票据绑定。

### 解释 B：服务端视为「同设备重新登录」

因为其它所有标识都没变，只有 GUID 变了 → 视为「同设备的票据刷新」。

**结合 NapCat 的实证**（"server validates the session ticket against the
hardware fingerprint (Device GUID). If the GUID changes, the server
invalidates the stored ticket"）：

**B 更可能** —— **GUID 的作用是「票据绑定」，不是「设备识别」。**

## 这个区分很重要

| 用途 | 锚点 |
|---|---|
| **设备识别**（服务端判「这是哪台设备」） | QIMEI / AndroidID / 机型 / serial 等 |
| **票据绑定**（服务端判「这张票是不是这台机器的」） | **GUID** |

**所以**：
- 改 GUID → 票据作废 → 需重新登录，但**不会被当成新设备**
- 改机型/QIMEI → **会被当成新设备**，要求验证

**这解释了 V6 那次为什么要求「新设备验证」**（机型变了），而这次不需要（GUID 只影响票据）。

- ✅ 可控（hook generateGuid 生效）

但**不能指望换 GUID 就换设备身份**。
