## 一、为什么怀疑 SsoHomeReport

它是 `wup_dump` 里唯一高频持续上报的命令（230 次，2.7 天），
且命令名是：

```
trpc.gc_indust.device_report.SsoHome.SsoHomeReport
                ↑↑↑↑↑↑↑↑↑↑↑↑↑
                device_report —— 直指「设备上报」
```

**如果它携带设备指纹，那就存在一个此前完全没分析过的第 6 通道。**

---

## 二、载荷结构分析（A 级）

### 单条样本

```
1795632851553 trpc.gc_indust.device_report.SsoHome.SsoHomeReport
len=13 hex=0000000d080110fec1bba0a134
```

拆解：

```
0000000d          长度前缀 = 13（大端）
08 01             protobuf field 1, varint, 值 = 1
10 fec1bba0a134   protobuf field 2, varint, 值 = 1795597359150
```

`1795597359150` 毫秒 → `2026-11-26 02:22:39`

**就是当前时间戳。**

### 全量验证：230 条全部一致

```
len 分布:
    230  len=13          ← 无一例外

结构模式（全部 230 条）:
    0801 10 <varint>     （field1 = 1）
    0803 10 <varint>     （field1 = 3）

唯一载荷数: 230 个       ← 每个都是不同的时间戳
```

**230 条样本，全部 13 字节，全部只有 `类型 + 时间戳` 两个字段。**

### field 1 的两种值

| 值 | 出现 | 推测 |
|---|---|---|
| `1` | 多数 | 常规心跳 |
| `3` | 少数（启动初期出现） | 可能是初始化/状态变化 |

**两者都不携带设备信息。**

---

## 三、结论：命令名 ≠ 载荷内容

**`device_report` 只是 protobuf namespace 的命名，
不代表这个具体命令上报设备数据。**

这是一个方法论提醒：

> **不能靠命令名判断载荷内容，必须看字节。**

如果按名字推断，会误以为这是一个设备上报通道，
从而浪费一轮去「对齐」一个根本没有设备字段的命令。
